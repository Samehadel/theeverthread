# theeverthread application foundation

Existing installations: follow the [rename and deployment cutover](../docs/RENAMING.md) before starting the renamed stack.

Implementation of [BTF-3](https://linear.app/betterf/issue/BTF-3). Spring Boot backend, Angular shell, PostgreSQL, Liquibase, and automated checks. BTF-5 adds organization registration, administrator email verification, and password-based account access.

## Repository layout

The current Git checkout is rooted above this directory: application code lives under `app/backend` and `app/frontend`; CI lives at `.github/workflows/ci.yml`. The architecture repository is a separate sibling at `architecture/`. The original workspace source map describes a separate application checkout; this implementation preserves the root repository layout observed during setup. Run the commands below from `app/` unless another directory is stated.

## Prerequisites

- JDK 25 (`java -version`). `JAVA_HOME` must point to that JDK.
- Node 22.23.1 and npm 10.9.8 (`node --version`, `npm --version`). With nvm, run `nvm install` from `frontend/`.
- Docker Engine/Desktop running with Docker Compose v2 (`docker info`, `docker compose version`).
- Git, Bash, curl, and network access for initial Gradle/npm dependencies and PostgreSQL/Chromium downloads.

The checked-in Gradle 9.7.1 wrapper downloads its distribution and verifies the pinned checksum. No global Gradle install is needed. Backend framework versions are pinned in `backend/build.gradle`; resolved versions are locked in `backend/gradle.lockfile`. Frontend versions are exact and `package-lock.json` is committed.

## Prepare a fresh checkout

Clone the application repository and enter its `app/` directory:

```bash
git clone https://github.com/Samehadel/theeverthread.git
cd theeverthread/app
cp .env.example .env
```

Set `DB_PASSWORD` in `.env` to a new local-only value. A shell-safe value can be generated with `openssl rand -hex 24`. The launchers source `.env` as trusted local shell configuration; quote values containing shell metacharacters. Do not commit this file. No default password is provided.

```bash
docker compose up -d --wait
cd frontend
npm ci
cd ..
```

PostgreSQL listens only on loopback, uses database `theeverthread`, and persists in the project-owned `theeverthread_postgres-data` volume. On first startup PostgreSQL initializes credentials from `.env`. Changing `.env` later does not change a password already stored in that volume.

## Run

From `app/`, in separate terminals:

```bash
./scripts/backend.sh
```

```bash
./scripts/frontend.sh
```

Open http://127.0.0.1:4200 for the Orbit landing page. Open http://127.0.0.1:4200/status for the backend diagnostic screen, which should display **Connected**. Stop the backend, choose **Check again**, and confirm **Backend unavailable** appears. Restart the backend and choose **Try again** to reconnect.

```bash
curl --fail http://127.0.0.1:8080/actuator/health/readiness
curl --fail http://127.0.0.1:8080/actuator/health/liveness
curl --fail http://127.0.0.1:8080/api/status
```

Expected status body: `{"data":{"status":"UP"},"error":null}`. Readiness includes PostgreSQL; liveness does not. Liquibase initializes the application tables and records migration history on startup. Hibernate validates the resulting schema; schema mutation is disabled.

Use Ctrl-C in each application terminal and `docker compose down` to stop supporting infrastructure while retaining data. `docker compose down -v` deletes this project's database volume; use it only when its local data is disposable.

## Development database ID transition

Entity primary keys and their references use PostgreSQL `BIGINT`, generated independently per table with `GENERATED BY DEFAULT AS IDENTITY` and mapped to Java `Long`. Verification email rows share the account's generated key. IDs can have gaps and are not business sequence numbers. API entity IDs are decimal **strings**, including workspace headers, paths and link payloads; keep them as strings in JavaScript to avoid precision loss. Submission deduplication IDs and worker attempt/lease tokens remain UUIDs.

The original Liquibase SQL initialization scripts create bigint keys directly. There is no UUID-to-bigint conversion migration. Existing installations must be reset to **no application tables and no Liquibase history** before using these rewritten scripts; deleting rows alone is insufficient because old schema/checksums remain.

Stop every backend instance connected to the development database. Run the manual [reset SQL](backend/src/main/resources/db/reset-development.sql) once in **each intended development database**, then start the matching backend so Liquibase recreates the tables, foreign keys, indexes and sequences. For a PostgreSQL client:

```bash
psql --set=ON_ERROR_STOP=1 --dbname="$DATABASE_URL" --file=backend/src/main/resources/db/reset-development.sql
```

`DATABASE_URL` must be a PostgreSQL client connection string for the intended database (not a JDBC URL). The SQL deletes application data in `public`, dropping child tables before parent tables, application trigger functions and Liquibase history. Owned identity sequences are removed with their tables. It preserves the schema and unrelated tables, and intentionally avoids `CASCADE`: an unexpected external dependency aborts the transaction instead of removing that dependency. Adjust the schema qualification if an environment uses another application schema. Nothing runs this reset automatically.

Restart the backend and reload the frontend together. Previous account/ticket IDs, verification and invitation links, refresh cookies and pagination cursors are invalid after reset; register again and obtain new links. Existing authenticated sessions must also be discarded on backend restart.

The change retains workspace membership checks and random 256-bit verification/invitation/refresh secrets. Sequential identifiers never grant access on their own. The pagination cursor format is version 2 with numeric ID ordering.

Architecture baseline consulted: `cdd59b639c3136a6311640b7f403a5aca60af5ba` (`architecture/origin/main`).

## Configuration

| Variable         | Purpose / default                                            |
| ---------------- | ------------------------------------------------------------ |
| `DB_PASSWORD`    | Required local PostgreSQL password                           |
| `DB_USER`        | Required backend username; `.env.example` uses `postgres`    |
| `DB_PORT`        | Compose host database port, `5432`                           |
| `DB_NAME`        | Local Compose database name; defaults to `theeverthread` |
| `POSTGRES_VOLUME` | Local PostgreSQL volume; defaults to `theeverthread_postgres-data` |
| `DB_URL`         | Backend JDBC URL, `jdbc:postgresql://127.0.0.1:5432/theeverthread` |
| `SERVER_PORT`    | Backend port, `8080`                                         |
| `BACKEND_URL`    | Angular development proxy target, `http://127.0.0.1:8080`    |
| `SERVER_ADDRESS` | Backend bind address, `127.0.0.1`                            |

If changing `DB_PORT`, change the port in `DB_URL` too. If changing `SERVER_PORT`, update `BACKEND_URL`. Browser requests use relative `/api` URLs. The production frontend build requires a host serving the SPA and proxying `/api` on the same origin; production deployment is not supplied by this story.

Spring Security permits the status/probe endpoints and the documented registration and authentication endpoints. Mutations require CSRF; company access requires an authenticated account and active account/organization statuses. Unknown endpoints remain denied and no default development user is generated. The handwritten OpenAPI contract is `backend/src/main/resources/openapi.yaml`; it is packaged as a resource, not exposed as a public documentation endpoint.

## Verify

Backend checks run against their own disposable PostgreSQL container and do not use `.env` or the local development database:

```bash
cd backend
./gradlew check bootJar
cd ../frontend
npm test
npm run build
npx playwright install chromium
```

With the backend running (the browser runner starts its own Angular server on port 4200):

```bash
npm run test:e2e
```

If port 4200 is already occupied, run `E2E_PORT=4320 npm run test:e2e` to test on a separate port. If the backend uses a custom port, run `BACKEND_URL=http://127.0.0.1:YOUR_PORT npm run test:e2e`.

Backend coverage includes real startup/migration history, HTTP envelopes and exclusions, security denial, database outage/recovery, and Spring Modulith boundaries. Jest covers loading, success, malformed responses, service failure/retry, and timeout recovery. Playwright covers live backend communication, a browser-controlled network outage and real reconnect, keyboard interaction, and a narrow viewport. The outage interception verifies client recovery; the backend database outage is tested separately with a real paused PostgreSQL container.

Reports: `backend/build/reports/tests/test/index.html`, `backend/build/reports/jacoco/test/html/index.html`, and Playwright failure traces in `frontend/test-results/`. CI executes the same checks on Linux, installs Chromium, starts the packaged backend with PostgreSQL, and verifies browser communication.

CI runs backend checks and JAR packaging in the `backend` job and frontend
checks and the production build in the `frontend` job, each on a separate runner.
Both must succeed before the `verify` job downloads the tested JAR, installs
Chromium's headless shell, starts the local stack, and runs browser checks.
Publishing waits for `verify` and uses the original `backend-jar` and
`frontend-browser` artifacts. Backend and browser failures upload reports from
the runner where they occurred. Registration resend cooldown boundaries and
replacement links are covered by backend integration tests with a mocked clock.
PR checks run when a PR is opened, updated, or reopened.

To intentionally refresh dependency locks after editing versions, run `./gradlew dependencies --write-locks` in `backend/` and `npm install` in `frontend/`, then review lockfile changes and rerun checks.

## Troubleshooting

- **Docker unavailable:** start Docker Desktop/Engine and verify `docker info`. Integration tests require Docker and fail rather than silently skip.
- **Port already in use:** use an unused `DB_PORT` and matching `DB_URL` in `.env`; update backend/proxy ports together if necessary. This machine's verification used PostgreSQL port `55432` because `5432` was occupied.
- **Password authentication failed:** verify `.env` and remember existing database volumes retain their original password. Restore the original local password or deliberately recreate a disposable volume.
- **Backend will not start:** verify JDK 25, `DB_PASSWORD`, and `docker compose ps`. Initial dependency downloads require internet access. Liquibase/database failure must be fixed before readiness succeeds.
- **UI reports unavailable:** inspect the readiness URL, check `BACKEND_URL`, and restart Angular after changing proxy configuration. Requests time out after five seconds and the retry button remains available.
- **Browser tests cannot start:** stop the existing frontend on 4200, ensure backend readiness, and run `npx playwright install chromium`. Linux may need `npx playwright install --with-deps chromium`.
- **Changes to migrations:** do not edit already-applied changesets. Add a new SQL changeset and explicit include. The initial `SELECT 1` changeset has a non-destructive no-op rollback; future product migrations need their own recovery design.

## Organization registration (BTF-5)

The landing page links to `/register` and `/login`. Registration persists a pending
organization, pending account, and a separate reusable verification email record.
Only email verification activates the organization/account and establishes ADMIN
access. Pending organizations do not reserve domains; only one can become active
for a domain. Login requires both statuses to be ACTIVE.

New passwords require 10–128 characters, an uppercase letter, and a special
character (punctuation or symbol). Spaces alone do not satisfy the special-character
requirement. Browser and API apply the same checks; existing login passwords are
not revalidated against the new registration policy.

Opening a valid email link automatically submits the token to the CSRF-protected
verification API. First-time verification creates the authenticated session and
rotates the session ID and CSRF token; the browser goes directly to `/company`.
The `/verify` route is only a transient link handler, with recovery shown for invalid
or expired links. No email re-entry or confirmation click is needed for valid links.
An already-used link cannot create another session: an existing matching session
returns home, otherwise the page offers password login.

This follows the product owner's 2026-10-04 correction to BTF-5's earlier
no-company-status wording. Architecture baseline: `0765baaa675be6232b9df9c025d415dca1ab3f49`;
implementation decisions are in architecture ADR 0005.

## Transactional email

Registration and workspace invitation requests save their email obligations in the
same PostgreSQL transaction as their account or invitation changes. A background
worker submits queued mail to Resend every five seconds. The scheduler can be
disabled with `THEEVERTHREAD_REGISTRATION_DELIVERY_ENABLED=false` and its interval
set with `THEEVERTHREAD_REGISTRATION_DELIVERY_CRON` using Spring’s six-field cron format.
The default is `*/5 * * * * *`.

Each email has one stable request ID and an encrypted copy of its Resend payload
until submission ends. Automatic retries reuse the same ID and bytes for up to
23 hours from the first attempt. Resend retains idempotency keys for 24 hours.
An unresolved submission stops at the deadline with an unknown outcome. A confirmed
rejection or exhaustion after known rejections produces a failure. The application
tracks delivery after acceptance through signed webhooks and a periodic lookup
for up to seven days. A later signed outcome can resolve an unknown status.

The latest email is tracked independently of the account or invitation. A
confirmed replacement starts a new 24-hour verification or seven-day invitation
link lifetime. Until confirmation, the previous link retains its original expiry.
A recipient can use a link that reached them while delivery confirmation is
pending. Completing verification or accepting an invitation takes precedence
over subsequent email events.

### Resend configuration

Set `RESEND_API_KEY` to a key with permission to send and retrieve emails, and
`MAIL_FROM` to an address on a verified Resend domain. Set `PUBLIC_ORIGIN` to
the HTTPS browser origin. Supply `EMAIL_PAYLOAD_KEY` as a base64-encoded 32-byte
secret generated with `openssl rand -base64 32`. Keep the same key on all
application instances and across restarts. Drain queued submissions before
changing this key.

Register `POST /api/webhooks/resend` on the public origin in Resend. Subscribe to
`email.sent`, `email.delivery_delayed`, `email.delivered`, `email.failed`,
`email.bounced`, and `email.suppressed`. Store its signing secret in
`RESEND_WEBHOOK_SECRET`. Use full-access credentials for retrieval and keep them in
the deployment secret store. [Resend keys](https://resend.com/changelog/new-api-key-permissions)
and [webhook verification](https://resend.com/docs/webhooks/verify-webhooks-requests).

Stop the previous release before rolling out the migration. Previously usable
links keep their expiry. The new worker imports pending verification work and
known legacy failures that were scheduled to retry. Legacy accepted or in-flight
submissions with no definitive outcome are recorded as unknown. A cross-provider
automatic replay would have no deduplication guarantee.

### Trace an individual email

Use the API's `emailReference` or look up the recipient and creation time in
`EMAIL_OUTBOX`. Check `PROVIDER_ID` in Resend for the provider timeline and query
the recorded submission attempts, poll results, and webhook outcomes in PostgreSQL.

```sql
SELECT id, status, created_at, accepted_at, provider_id, failure_code
FROM email_outbox
WHERE recipient = :normalized_recipient
ORDER BY created_at DESC;

SELECT occurred_at, recorded_at, kind, reason
FROM email_delivery_event
WHERE email_id = :email_reference
ORDER BY recorded_at, event_key;
```

Delivered means the recipient's mail server accepted the email. Inbox placement
is determined by the receiving provider.

## Team invitations

Workspace owners can invite one recipient at a time and view or resend eligible
invitations from **Manage your team**. The form locks a queued row and offers
**Add another invitation**. Owners can check delivery status from the form or
refresh it on **Sent invitations**.

`INVITATION_MAX_ACTIVE_ACCOUNTS` sets the default cap of 10 active members,
including the owner. A positive `WORKSPACE.MAX_ACTIVE_ACCOUNTS` overrides it.
Pending invitations reserve no slots. The recipient explicitly accepts at
`/invitation/accept`, using an existing account or completing registration.
Used links direct recipients to sign in.

## Session expiry recovery

The browser now restores expired sessions through `POST /api/auth/refresh` and retries
requests rejected by authentication before execution. Refresh credentials rotate and
live in a Secure, HttpOnly, SameSite=Strict cookie scoped to `/api/auth`; the database
stores only hashes. `REFRESH_TOKEN_LIFETIME` defaults to `14d` with an absolute expiry.
Logout revokes this browser's refresh credential. Password changes and inactive
accounts prevent renewal; workspace access is revalidated separately. Sessions established before this deployment
need one new login to obtain a refresh cookie.

Anonymous protected requests now return `401 AUTHENTICATION_REQUIRED`; CSRF rejection
returns `403 CSRF_INVALID`, and permission denial remains `403 ACCESS_DENIED`. The UI
refreshes CSRF after restoration and does not replay network failures or generic
permission errors. Exhausted refresh credentials lead to login. Concurrent requests
share recovery; browsers supporting Web Locks also coordinate across tabs.

Apply the additive refresh-session migration with the backend deployment and deploy
the matching frontend. Architecture consulted: `16a2955` on architecture `origin/main`;
the proposed decision is in `architecture/decisions/0005-session-refresh.md`.

## Knowledge capture and monitoring

Active members and administrators can open **Capture knowledge** from Knowledge. Title and Details are required; Capture is optional. Refine Title or Capture
independently using the side panel's Proofread (mechanics), Rephrase (clarity),
or Rewrite (substantial restructuring) action buttons. Clicking an action immediately
requests a suggestion for that field. Compare the original and suggestion in the
same panel and explicitly accept or discard. Field shortcuts reach the corresponding
panel section on mobile; accepting returns focus to the updated field. The API
accepts an optional `mode`; omission retains Proofread for older clients. Refinement
uses only the selected field's existing text; blank Capture cannot be refined. Prompts live
in backend `resources/prompts/knowledge/*.st`. Details are never refinement context.
The Writing Studio publishes immediately, then classifies in the background.
Set the server-only `OPENAI_API_KEY` for Spring AI ChatClient with OpenAI
`gpt-5.4-nano`. Startup requires a nonblank API key. After startup, AI suggestions
are optional; an unavailable provider does not prevent
publication. Title, Capture, and Details are sent to the provider without author or
workspace metadata. Content sanitization is deferred by the product owner's
explicit decision, so embedded sensitive text is not redacted.

Classification makes up to three attempts and preserves publication on failure.
`theeverthread.knowledge.classification.enabled=false` disables the scheduler;
`theeverthread.knowledge.classification.delay` changes its five-second default interval.
The classification catalog is seeded by Liquibase in `KNOWLEDGE_ATTRIBUTE`; active
definitions and display labels are read from the database. The catalog update
procedure, model evaluation command, result
versioning, and selective legacy reclassification runbook are documented in
[Automatic capture classification](../docs/CLASSIFICATION.md).

Public Actuator probes are `/actuator/health/liveness` and
`/actuator/health/readiness` (database readiness). `/actuator/info`, `/actuator/metrics`, and
`/actuator/prometheus` are denied to ordinary product accounts; workspace ownership grants no platform operator access. JVM and HTTP metrics
are available; `theeverthread.knowledge.classification` records completed and failed
classification attempts. The deployment proxy forwards these protected endpoints;
no deployment has been performed as part of this story.

The knowledge ChatClient and model initialize lazily and share the application's
observation and meter registries. OpenAI calls use `reasoning-effort: none`,
`store: false`, 2,048 completion tokens, a 45-second timeout, and zero retries.
The browser and proxy allow 50 and 55 seconds respectively for refinement.
`SimpleLoggerAdvisor` is installed with advisor parameter `provider=openai`.
Its request/response logging is available at DEBUG via
`logging.level.org.springframework.ai.chat.client.advisor.SimpleLoggerAdvisor=DEBUG`.

## Accounts and workspaces

`/signup` requests full name, email and password. Email activation creates a ready-to-use default workspace. `/register` redirects to signup; the organization registration flow is removed. The workspace picker selects among memberships. Open **Workspaces** in the navigation (`/workspace/settings`) to create a workspace or rename one you own. Names are unique per owner, ignoring capitalization and surrounding whitespace; successful changes update the existing picker. Signup assigns the default workspace automatically; users do not need a create-workspace step.

Workspace invitations add membership alongside the default workspace. Existing accounts sign in and explicitly accept; pending accounts use their original password. Invitations never replace credentials or existing memberships. New social signup is unavailable in this delivery; stored provider links and trusted linking/login support remain intact.

Deploy the matching backend and frontend after taking a database backup and stopping old backend instances. The new versioned workspace migration preserves existing IDs, credentials and content and replaces organization/account classifications with workspace memberships. Invalidate old sessions at rollout. Restore the backup and old binaries for rollback; do not run old binaries against the new schema.

Knowledge and invitation APIs require `X-Workspace-Id`. See [OpenAPI](backend/src/main/resources/openapi.yaml) and [workspace identity design](../architecture/backend/workspace-identity.md).
